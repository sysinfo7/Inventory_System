## Implemented application behavior

- Application sign-in uses database-backed app users, salted scrypt password hashes, opaque hashed server sessions, and server-enforced Administrator, Manager, Clerk, and Read-only roles. New product and stock writes use the authenticated account as audit actor. Migrations 008-010 add the account/session schema, actor-aware product write function, and actor foreign keys.
- Initial administrator and optional random-password test accounts are created by local-only, documented scripts; test accounts are opt-in.

- Product catalog: search, active/inactive filtering, create/edit, and deactivate through the controlled `save_product` function.
- `/stock`: selected-location balances for active products, reorder attention, receiving and customer-return forms for stock clerks, sale deductions, and manager/administrator count adjustments.
- `/activity`: location, movement-type, and name/SKU/reason filters; newest-first signed movement rows, capped at 200 results.
- `/activity`: also filters by recorded-by actor (including legacy entries) and inclusive UTC date range; invalid or reversed date inputs do not reach the database query.
- Migration 015 adds global timestamp and non-null actor/timestamp indexes to support the activity ledger's newest-first and actor-filtered queries.
- The overview page stays static and no longer repeats the per-request session database lookup already performed by the navigation header. This keeps the main page from triggering Next.js's uncached-data-during-navigation insight.
- At phone width, movement history presents all seven fields as a stacked card, keeping the signed change and recorded-by actor visible without horizontal scrolling.
- The permissions matrix, user management, and permission-denied pages isolate request-specific account checks behind route-level Suspense boundaries and start request-time data work after `connection()`.
- Stock writes call `record_stock_movement` through `APP_DATABASE_URL`, passing the verified signed-in user's UUID as actor. The function validates active product status, direction, reason, request-token idempotency, and nonnegative balances transactionally.
- Customer returns are positive inventory movements available through the stock-receiving permission. Count adjustments require a reason and explicit add/remove direction; only managers and administrators have `stock:adjust`.
- Administrator account management can create, activate, and deactivate accounts; users cannot deactivate themselves or the last active administrator. Manager, Clerk, and Read-only test accounts are opt-in and use generated passwords.
- PostgreSQL revokes every existing session when an account role changes or its active flag changes to false. Reactivating an account does not restore previous sessions.
- Supplier purchasing: new pages and actions add searchable suppliers/products, role-gated supplier maintenance, quantity-only draft orders, submitted label snapshots, partial/final receiving into the destination, receipt history, and cancellation of remaining quantities with a reason. Receipt and stock ledger changes use one database transaction and exact retries cannot duplicate movements. New DB role checks supplement server permissions. No supplier costs, currency, invoice/payment, tax, or accounting records are implemented. Migrations 019–021, the rollback-only purchasing verifier, and a live admin browser walkthrough passed locally. The walkthrough created `Demo Wholesale Supply` and completed `PO-00000007` for five coffee units at Demo Outlet, receiving two then three units. Both receipt movements are visible in activity history; Demo Store remains at seven coffee units. The local demo also contains submitted order `PO-00000018` for three Summit Steel Water Bottles at Demo Store; its current progress is 0/3 and stock is unchanged. The CI-only two-session receipt race verifier also passed on [main commit 6f6abc6](https://github.com/sysinfo7/Inventory_System/actions/runs/38654409673). The manual includes screenshots of the order register and each order state, including the receipt form.
- Login attempts are reserved atomically in PostgreSQL before password verification. Eight attempts per normalized email/client pair or 100 per client are allowed in a 15-minute window; successful login clears that email/client bucket. HMAC keys use the app connection secret, and expired hashes are pruned in bounded batches. The auth verifier confirms the threshold, retry interval, and least-privilege table access.
- Migration 016 adds an append-only `app_security_events` table. A user can change their own password after current-password verification; the database trigger logs only the subject UUID, event type, and timestamp, then revokes all sessions atomically. The runtime role cannot read or write the security-event table. Local migration, database, stock, lint, typecheck, and full auth checks passed; CI also exercises password-change behavior in its disposable database.
- Migrations 017–018 add the forced-password-change flag, administrator-reset event type and actor UUID. Administrators can reset a different active account with a temporary password; existing sessions are revoked, the user must set a new password before protected access, and a concurrent old-password login cannot establish a surviving session. Temporary passwords are never displayed again by the app or stored in plaintext.
- The authentication verifier now removes its temporary user with the local database administrator connection. Run `npm run auth:cleanup-checks` once to remove temporary users left by earlier verifier versions.
- These are quantity records; they do not process payments or create accounting entries. Persistent account lockout and recovery remain future security work.
